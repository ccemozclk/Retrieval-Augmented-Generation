# Hands-On RAG from Scratch: Comparing Chunking Strategies

An end-to-end **RAG (Retrieval-Augmented Generation)** pipeline built with LangChain v1. It covers document loading, chunking, embedding, retrieval, answer generation and evaluation. The focus of the project is **comparing chunking strategies on the same data and measuring the results**.

📓 **Kaggle (with outputs):** [Kaggle link]

## Scenario

A **customer support assistant** for *Mavi Resif Akvaryum*, a fictional aquarium company. The assistant answers questions from four documents:

| Document | Structure | Why it was chosen |
|---|---|---|
| `bakim_rehberi.md` (care guide) | Headings and a table | To test layout-aware chunking |
| `hastaliklar.md` (fish diseases) | Headings, short sections | To test section-based splitting |
| `iade_politikasi.txt` (return policy) | Plain text | To test recursive splitting on unstructured text |
| `musteri_gorusmesi.txt` (customer call) | Transcript that jumps between topics | To test semantic chunking |

The assistant cites its sources and says it doesn't know when a question is not covered by the knowledge base.

> All data is fictional and generated by the notebook itself. The documents and prompts are in Turkish, and the pipeline uses a multilingual embedding model.

## Chunking methods at a glance

| Method | Core idea | Best suited for |
|---|---|---|
| Recursive | Split hierarchically by text structure | Rapid prototyping, general text |
| Semantic | Split where the meaning shifts | Transcripts, blog posts, narrative text |
| Layout-Aware | Split by the document's own headings and format | Corporate reports, manuals, PDFs, HTML |
| Small-to-Big | Search small chunks, pass the larger parent chunk to the LLM | Most production RAG systems |
| Agentic | Let an LLM decide the splits | Small sets of high-value documents |

## Key takeaways

- **RAG is not an advanced form of fine-tuning; it's an alternative.** Fine-tuning shapes how the model talks, RAG shapes what it knows.
- **Most bad answers come from retrieval, not the LLM.** Debugging should start by inspecting the retrieved chunks.
- **Naive splitting can cut a table in the middle of a row.** Values separated from the header row lose their meaning.
- **Measure chunk size with the embedding model's own tokenizer.** Anything over the model's token limit is silently truncated.
- **Use `ensure_ascii=False` when splitting JSON with non-English text.** Otherwise characters turn into escape codes and the embeddings degrade.
- **The best chunking strategy is the one you measure on your own data.**

## How to run

### Kaggle
1. Open the notebook on Kaggle and click **Copy & Edit**.
2. *Settings* → **Internet: On**.
3. *Add-ons* → **Secrets** → add `ANTHROPIC_API_KEY` and attach it to the notebook.
4. **Run All**.

### Locally
```bash
git clone <this-repo>
cd <this-repo>
pip install -r requirements.txt
cp .env.example .env        # put your own ANTHROPIC_API_KEY in .env
jupyter notebook rag_uygulamali.ipynb
```

> The chunking, embedding and retrieval cells run without an API key, since the embedding model runs locally. The key is only needed for the cells that call the LLM: agentic chunking, MultiVector, answer generation and CAG.
